Bolo — v0.7 Addendum: TTS Fallback & Graceful Degradation
Purpose: A focused supplement to bolo_v07_plan_final.md covering exactly how the app behaves when audio clips are partially present, partially missing, or fully missing. Worth pinning down because real recordings will arrive in batches — Sabrina might finish first, Sameer a week later, etc.

1. The principle
The app must work fully and never crash regardless of which audio clips exist. Concretely:

All clips missing (today's state): every phrase uses device TTS reading the Roman text. App is fully functional.
One voice pack complete, others missing: picking the complete pack uses real audio; picking an incomplete pack uses real audio where available and TTS where missing — silently, no error.
Partial within a voice pack: clips 1-5 real, clips 6-10 missing → first 5 are human voice, last 5 are TTS. The user shouldn't see any visible error.
All clips present: TTS never fires.

This means the app remains demoable at every stage of the recording pipeline, from "no audio yet" to "all 4 voice packs complete."

2. Audio resolution logic (final spec)
The audioService.playPhrase(phrase, speed, voicePackOverride?) flow:
1. Determine which voice pack to use:
   - If voicePackOverride is set → use it
   - Else → useChapterStore.getState().activeVoicePackId
   - Else fallback → useUserStore.getState().defaultVoicePackId
   - Else fallback → "sabrina"

2. Resolve the path:
   - path = phrase.audio[voicePackId]?.[speed]
   - If path is undefined → go to TTS fallback (step 4)

3. Look up the path in the audio map:
   - asset = audioMap[path]
   - If asset is undefined → go to TTS fallback (step 4)
   - Otherwise → play via expo-av Audio.Sound.createAsync(asset)

4. TTS fallback:
   - Speech.speak(phrase.roman, {
       language: 'ur',
       rate: speed === 'slow' ? 0.6 : 0.85,
     })
   - Log once (DEV only): `[audio] TTS fallback for ${path}`
Critical detail: the audio map check (step 3) is the actual gate. Even if phrase.audio.sabrina.normal is a string, if no file exists at that path, the auto-generated audioMap.ts won't contain a require() for it, so the lookup returns undefined. That's the trigger for the fallback. No try/catch needed.

3. Audio map regeneration as the source of truth
The audioMap.ts file is auto-generated by scripts/generateAudioMap.ts. It walks assets/audio/ and emits one require() per file present.
Workflow when new clips arrive:

Recorder sends sabrina.zip (or whoever)
Unzip into assets/audio/C01/sabrina/
Run pnpm gen:audio
The audio map regenerates. Files that exist now resolve to require statements; files that don't are simply not in the map.
Rebuild the app (or hot-reload). New voices play; missing ones still fall back.

This is the cleanest design — there's no "audio missing" state to manage in the data. The presence or absence of a file on disk is the state, and the audio map reflects it.

4. UI affordances during the transition
A few small touches to make the partial-audio experience feel intentional, not broken:
4.1 In the voice pack picker
When the user previews a voice pack:

If the preview phrase audio exists → it plays from the real recording
If it doesn't exist → it plays via TTS, with a small italic note under the preview button: "Voice coming soon — preview using synthetic voice"

This sets expectations honestly without breaking the picker.
4.2 In the voice pack metadata
Add an optional recordingStatus field to each voice pack in voicePacks.json:
json{
  "id": "sabrina",
  "displayName": "Sabrina",
  "recordingStatus": "complete",
  ...
}
Possible values:

"complete" — all clips recorded for Chapter 1
"in-progress" — some clips exist
"pending" — no clips yet

For now: set all four to "pending". When Sabrina sends her zip, flip hers to "complete". The picker uses this to show small status badges ("Coming soon" / "New!" / nothing).
This is optional polish — the technical fallback works without it. But it makes the demo more honest.
4.3 No error toasts to the user
Never show a user-facing error like "audio file missing." The TTS fallback is the answer. The only "error" reporting is a DEV-only console log so you can see what's missing during development.

5. Boss scenario fallback nuance
The boss scenario speaker (the auntie) is locked to Sabrina via speakerLine.voicePackId: "sabrina". The fallback applies normally:

If audio/C01/sabrina/scenario-turn1.m4a exists → real auntie voice
If not → TTS speaks the Roman of the auntie's line

For the boss scenario specifically, the TTS fallback is uglier because the auntie's lines aren't standard learner phrases — they're conversational. Robotic TTS saying "Yeh aap ke liye" sounds notably worse than robotic TTS saying "Shukriya."
Mitigation: prioritize Sabrina's scenario clips. If only some clips can be recorded in the first session, the order of priority should be:

Sabrina's 4 scenario clips (highest demo impact — the boss is the marquee moment)
Sabrina's 20 phrase clips (the default voice for new users)
Sameer / Daniyal / Taha phrase clips (in any order)


6. Code change: updated audio service skeleton
For reference during Sprint B implementation:
typescript// services/audioService.ts
import { Audio } from 'expo-av';
import * as Speech from 'expo-speech';
import { Phrase, VoicePackId } from '@/types/phrase';
import { useChapterStore } from '@/stores/useChapterStore';
import { useUserStore } from '@/stores/useUserStore';
import { audioMap } from './audioMap';

let currentSound: Audio.Sound | null = null;

async function stopCurrent() {
  if (currentSound) {
    try { await currentSound.unloadAsync(); } catch {}
    currentSound = null;
  }
  try { await Speech.stop(); } catch {}
}

function resolveVoicePack(override?: VoicePackId): VoicePackId {
  if (override) return override;
  const active = useChapterStore.getState().activeVoicePackId;
  if (active) return active;
  const defaultPack = useUserStore.getState().defaultVoicePackId;
  return defaultPack ?? 'sabrina';
}

async function playFromAsset(asset: number) {
  const { sound } = await Audio.Sound.createAsync(asset, { shouldPlay: true });
  currentSound = sound;
  sound.setOnPlaybackStatusUpdate((status) => {
    if (status.isLoaded && status.didJustFinish) stopCurrent();
  });
}

function playFromTTS(roman: string, speed: 'normal' | 'slow') {
  Speech.speak(roman, {
    language: 'ur',
    rate: speed === 'slow' ? 0.6 : 0.85,
  });
}

export const audioService = {
  async playPhrase(
    phrase: Phrase,
    speed: 'normal' | 'slow' = 'normal',
    voicePackOverride?: VoicePackId
  ): Promise<void> {
    await stopCurrent();
    const packId = resolveVoicePack(voicePackOverride);
    const path = phrase.audio[packId]?.[speed];

    if (path && audioMap[path]) {
      await playFromAsset(audioMap[path]);
    } else {
      if (__DEV__ && path) {
        console.log(`[audio] TTS fallback (no asset for ${path})`);
      }
      playFromTTS(phrase.roman, speed);
    }
  },

  async playUri(uri: string): Promise<void> {
    await stopCurrent();
    const { sound } = await Audio.Sound.createAsync({ uri }, { shouldPlay: true });
    currentSound = sound;
    sound.setOnPlaybackStatusUpdate((status) => {
      if (status.isLoaded && status.didJustFinish) stopCurrent();
    });
  },

  async stop(): Promise<void> {
    await stopCurrent();
  },

  isPlaying(): boolean {
    return currentSound !== null;
  },
};
Three key behaviors guaranteed by this design:

TTS is the default until proven otherwise. Every clip starts in "TTS land" and graduates to "real audio" only when the file is on disk and gen:audio has been run.
No crash path. The worst that can happen is TTS plays in place of human voice.
Voice pack switching works regardless of recording state. If the user picks "Taha" but Taha has no clips yet, the entire app uses TTS for Taha's content — but the user still gets a working experience and can switch back to Sabrina (who might be complete) any time.
